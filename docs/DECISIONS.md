# Decisions and assumptions (platform build)

Product-behaviour decisions (what to collect, hold vs confirm, escalation, etc.) from the prototype are in `02_decision_register.md` and carry over; this file records build decisions.

1. **No `/reference` folder was supplied** (no brief PDF, seed SQL, data dictionary, ER diagram). Schema was taken by introspecting `data/setuhaul_freight_operations.db`; prototype notes live in `docs/`.
2. **Seed source** is that SQLite file. It is a *working copy* (extra tables `agent_holds`, `agent_audit_log`; more rows than the pristine snapshot: 150 chat messages, 26 appointments, 28 ETA updates). It is seeded as-is; the two extra tables are not carried (superseded by `slot_holds` and `audit_log` in later milestones).
3. **Keys**: surrogate UUID PKs (deterministic uuid5 in the seed, so re-seeding is idempotent); original ids (`SHP1002`, `THR003`, ...) kept as unique `code`. Tables without a business id (eta_updates, contacts, rules, dock events, check-ins, operational messages) have no `code`.
4. **Booleans** are native `boolean`; text timestamps (already ISO with +05:30) become `timestamptz`; `open_time/close_time` become `time`.
5. **Integrity** added beyond the reference: `EXCLUDE USING gist (dock_id =, tstzrange(start,end) &&)` on slots (needs `btree_gist`); partial unique indexes recreated with boolean `is_current`.
6. **Views** recreated against UUID keys and expose `*_code` columns for readability.
7. **No cross-module ORM relationships** to keep module boundaries (see CLAUDE.md).
8. **Drivers seeded as WhatsApp-verified** (`whatsapp_number = phone`, opted in, `en`) so the simulator works on seed data; real onboarding uses the verification flow.
9. **Python**: target 3.12 in Docker; local machine has 3.14, so all Python commands run in containers. `httpx` pinned `<0.28` for litellm compatibility.
10. **`chat_threads.taken_over_by_user_id`** is deferred to Milestone 1 (needs `users`).
11. **Pace**: milestone-by-milestone, per user choice.
12. **Layout**: two top-level folders, `backend/` (was apps/api) and `frontend/` (was apps/web), per user request; `infra/` and `docs/` stay at root.
13. **Auth**: access JWT (15 min) carries a session id checked against `sessions` on every request, so logout / force-logout / disable take effect immediately; refresh token rotates on each refresh. CSRF is double-submit (`csrf_token` cookie + `X-CSRF-Token`). Frontend reaches the API same-origin via a Next rewrite.
14. **Invites**: no email service yet, so `POST /users` returns the one-time `invite_token` to the admin. TOTP and self-service password reset are deferred (planned M10 hardening).
15. **Audit**: one SQLAlchemy session hook records every ORM insert/update/delete with actor, IP and trace id; secrets are masked. Raw-SQL writes (seed scripts) bypass it by design.
16. **Events**: SSE is backed by a Redis Stream (resume with Last-Event-ID); each event carries facility/carrier scope and is filtered per principal.
17. **Hold TTL** default is 15 min per the platform spec (the prototype used 5).
18. **Test hashing** uses cheap argon2 parameters when `ENV=test`.
19. **Shipment creation** leaves carrier/driver/vehicle empty (columns made nullable) with `offer_status` draft -> offered -> accepted/declined; carrier users never see drafts. Default planned ETA = facility opening time on the requested date (next day if none).
20. **Cancelling a shipment that holds an active appointment is blocked (409)** until the booking service (M4) can release the slot safely.
21. **Idempotency-Key**: middleware replays 2xx JSON responses per (session, method, path, key) for 24h via Redis.
22. **CSV import** is atomic (any bad row rejects the whole file) with a dry-run preview; exports neutralise spreadsheet formula injection.
23. Frontend dev port is **2000** (user request); the API stays on 8000.
24. **Schedule grid state precedence**: completed/in-progress > dock event (breakdown, maintenance, reduced capacity) > blocked slot > pending/confirmed > open. A confirmed booking under a dock event still shows its appointment so the planner sees the conflict. Holds are shown once `slot_holds` exists (M4).
25. **Blocking slots with live bookings** needs `force=true` after the planner sees the affected bookings. Automatic re-plan exceptions for coordinators arrive with the booking engine (M4/M6); until then affected bookings are listed and the `schedule.changed` event is published.
26. **Drag-and-drop move** and **suggest another slot** on pending confirmations are deferred to M4 (they need feasibility + re-validation).
27. **Facility rules** are validated per known type; when two active rules of one type overlap in time, the latest `effective_from` wins. Contact edits are allowed to planners of the facility (`docks_slots_rules` W) in addition to admins.
28. **Seed data is dated 2026-08-04**; the UI offers a jump to dates that have slots (`/slots/dates`).
29. **Booking lifecycle reads** (M3 part B): `modules/booking/readers.py` and `modules/analytics/repository.py` read facility, dock, slot, facility-rule and check-in tables directly and read-only, because those modules had no matching service functions yet. All writes stay in appointments/facility_checkins (plus `shipments.service.set_status`). Fold into the owning services when M4 lands.
30. **Yard rules**: arrival is EARLY if check-in is more than 15 min before slot start, LATE if after slot start + NO_SHOW_GRACE_MIN (facility rule, else setting `noshow_grace_minutes`, default 30), else ON_TIME. On time + planned dock free -> CALLED_TO_DOCK. Carrier users get 403 on all facility-operations endpoints (yard, inbound, pending, reports, facility-home).
31. **Inbound trucks** = shipments with a driver, not COMPLETED/CANCELLED, whose effective ETA or slot start falls on the chosen facility-local date. At risk = not late and (no appointment, LOW confidence, or ETA within 30 min of slot start).
32. **Utilisation report**: available minutes = OPEN slots plus any booked slot; booked = slots with a PENDING/CONFIRMED/IN_PROGRESS/COMPLETED appointment; blocked/closed unused slots are excluded.
33. **Slot claims (M4)**: a hold or live appointment claims every slot it covers in `slot_claims`, protected by `UNIQUE(slot_id) WHERE active`. This is how multi-window bookings (consecutive slots for long unloads) get the same database-level "one active booking per slot" guarantee as single slots. Alongside it: one active hold per slot and per shipment, and the original one-active-appointment indexes. Seeded active appointments were backfilled into claims in migration 0006.
34. **What an option, hold and booking mean**: options are read-only (never reserve). A hold is a time-limited, non-binding reservation (default 15 min, max total 60). Only CONFIRMED is a promise. A shipment holds one slot at a time (a new hold releases the old one); repeating the same hold is idempotent.
35. **Concurrency**: `place_hold` locks the slot rows `FOR UPDATE` in id order (no deadlocks), re-validates feasibility, then inserts. Losers get 409 `SLOT_TAKEN`; options that stopped being feasible get 409 `SLOT_UNAVAILABLE` with reasons. Expired-but-unswept holds are expired inline when someone wants the slot.
36. **Approval after hold expiry**: succeeds only if the slot is still free and the shipment holds nothing else (otherwise SLOT_TAKEN / HOLD_EXPIRED); a revived hold gets 5 minutes. Approving twice returns the same appointment.
37. **Starts after the last-allowed start (21:00)**: approval creates `PENDING_CONFIRMATION`; the shipment's old appointment stays current until a planner confirms (then it is replaced), is rejected, or the pending request expires (30 min) - the driver never loses their slot while waiting. Pending confirmation re-validates everything except the ETA.
38. **Ranking**: option ranking = approval-free first, earliest start, least spare time, dock code. Competing-request ranking = fixed (already unloading) first, then a weighted score (priority 1000, lost appointment 100, waiting 10/h, earliest start 1/h; tunable in `ranking_weights`); exact ties are flagged for a human.
39. **ETA**: effective ETA = latest ETA update (history never overwritten); a range uses its upper bound (`declared_eta_upper_ts`); a range or LOW-confidence ETA sets `requires_human_review`.
40. **No feasible slot** never invents an answer: `escalate_if_none` opens an `escalations` row with a hand-off record (shipment facts, ETA, rejection counts, current appointment).
41. **Dock events / forced blocks** create `approval_requests` with reason `REPLAN_DOCK_EVENT` / `REPLAN_SLOT_BLOCKED` in the same transaction so coordinators see what to re-plan.
42. **Outbox**: every booking state change writes an `outbox_events` row in the same transaction; delivery (WhatsApp/email/in-app) is M6/M8. The sweeper (arq cron, every minute) expires holds and pending confirmations, marks no-shows (last 24 h only, so seeded history is never rewritten) and flags stale ETAs.
43. **Still direct reads**: booking/readers.py continues to read facility, dock, slot and rule tables directly (decision 29); not yet folded into the owning services.
44. **Carrier portal reads** (M5 part B): `modules/carriers/portal_repository.py` joins shipments, appointments, slots, docks, check-ins, holds, approval requests, escalations and drivers directly and read-only (no service exposes this view yet). Every query starts from `base_shipments`, which carries the carrier scope; carrier users are pinned to their own carrier and a different `carrier_id` is a 404. Planners are excluded from `/carrier/*` and `/reports/carrier*`.
45. **Notifications**: role-addressed rows (optionally narrowed to a carrier or facility) with per-user read state in `notification_reads`; the audit hook ignores `notifications` and `notification_reads` (their origin events are already audited). The outbox worker (`process_outbox`, arq every 10 s) projects events into notifications, retries failures with backoff (max 5 attempts) and `run_outbox` publishes `notification.created` live events after the commit.
46. **Tracker `hold_state` precedence**: request_suggested > request_waiting > pending_confirmation > held (unexpired holds only) > none. Slot-changes shows one entry per appointment (its latest state), plus active holds, suggested/rejected/held requests and escalations.
47. **Assignment rules (M5)**: a vehicle that cannot carry the load is blocked (no refrigeration for temperature-controlled/reefer loads, not heavy-capable for heavy loads, load over capacity, type not allowed for the carrier, inactive driver/vehicle); a busy driver, a busy vehicle, or an unverified/opted-out WhatsApp number only warns. Assigning needs an accepted offer; changing it later is a reassign with a recorded reason that notifies coordinators.
48. **WhatsApp verification**: a hashed six-digit code (10 min, 5 attempts, 5 requests/hour) queued as an outbox message with the code encrypted; M8's sender delivers it and the driver's reply calls the same check. The API returns the code only outside production, to demo without a Meta account. Changing a number clears verification and opt-in.
49. **Test hygiene**: tests must not depend on the wall-clock hour (a yard test failed after 22:00 IST because slots fell outside operating hours); fixtures now use 10:00 IST on a future day.
50. **Coordinator desk reads (M6 part B)**: `modules/coordinator/desk_*_repository.py` and `desk_activity_service.py` read chat, driver, shipment, user, approval/hold/escalation, operational-message and audit tables directly and read-only (no service exposes these joins yet). All writes (takeover, hand-back, reply, handover save) go through ORM so the audit log records them. Fold into owning services later.
51. **Desk access**: desk reads (threads, board, handover, activity) are open to coordinators and admin only (planners and carriers get 403 even though planners hold `booking_decisions` R); writes need `escalations_takeover` W, which only coordinators have. Admin can read the handover history and drafts but not write one.
52. **Conversation takeover** is a single owner stored on `chat_threads.taken_over_by_user_id`: a second coordinator gets 409 `CLAIMED` naming the owner; only the owner can hand back (409 `NOT_OWNER`) or reply (409 `NOT_TAKEN_OVER`). A reply is saved as an OPERATIONS message and queued as a `whatsapp.send` outbox event (delivery in M8); the response says `deliverable:false` when the driver has no verified, opted-in WhatsApp number. Drafts are rule-based (en/hi, fallback en) until the AI route exists in M7; `translation` is null until M7.
53. **Live board** stages: unloading=IN_DOCK, in_yard=AT_GATE/WAITING, done=COMPLETED with unload end on the date, late=not yet at the gate and ETA after the slot start or overdue by more than 15 min, travelling=the rest; dates are read in each facility's time zone. Handover snapshots are recomputed on the server when saved, and the brief is deterministic text (AI summary in M7).
54. **Coordinator inbox** (M6): open requests, escalations and expiring holds are read with small read-only queries on booking tables, other kinds through their owning services. Only the coordinator role (capability `escalations_takeover` W) may use the desk; admin and planners get 403.
55. **Soft locks** are Redis keys with a 10-minute TTL, shown by owner name. A decision by anyone but the owner is refused (409 CLAIMED); an unclaimed item may be worked directly; a crashed browser frees the item on its own.
56. **Recommendation** is a pure rule function (approve / suggest / hold / escalate with reasons, impact and risk flags), labelled `source: "rules"`. Milestone 7 may add AI wording only; the action stays rule-derived and a human decides.
57. **Driver messages after decisions** are `whatsapp.template` outbox events using the reviewed template names (appointment confirmed / changed / request awaiting approval / escalation notice); slot, dock and times are inserted by code. A pending-planner approval uses `request_awaiting_approval`, a replacement uses `appointment_changed`, a rejection uses `appointment_changed` with outcome `not_possible`.
58. **Escalate** releases any hold, leaves the driver's current booking untouched, marks the request `escalated` (new status, migration 0009) and opens an escalation with a hand-off record.
59. **Competing requests** are open requests whose best option shares a slot. The pure ranking policy orders them; choosing a different winner needs a written reason (>= 10 chars) stored on the request and in the audit log. Hold extension is capped at the max-hold setting (60 min).
